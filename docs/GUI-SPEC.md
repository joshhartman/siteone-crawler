# SiteOne Crawler GUI — specification

Status: implemented (phases 1–8; 1–5 reviewed); describes the built application · Target: Windows 11
(x86_64, MSVC) · Language: Rust

A native desktop front end for the `siteone-crawler` CLI. It lets a person configure a crawl,
watch it run, read the results and return to earlier runs — without touching a terminal, and
without hiding the CLI: every setting maps to one CLI option and the exact command is always
visible.

---

## 1. Goals and non-goals

### Goals

1. **Intuitive first run.** URL + one click starts a useful crawl. Presets cover the common jobs.
2. **Complete.** Every crawl option of the CLI (226 options, 18 groups) is reachable, searchable
   and explained, generated from the CLI's own option metadata so the GUI cannot drift from it.
3. **Live.** Progress, URLs, AI activity, issues and console output update while the crawl runs.
4. **Robust.** The GUI never parses human-readable output for state. It never crashes on bad
   input, a missing binary, a killed child, a corrupt settings file or an unknown event. A crawl
   never outlives the GUI.
5. **Transparent.** A live command preview shows the equivalent CLI call; a profile exports to
   the CLI's config-file format.
6. **Persistent.** Profiles (saved configurations) and a history of runs survive restarts.

### Non-goals (v1)

- macOS/Linux packaging (the code stays portable; only Windows is built and tested).
- Running several crawls at once; scheduling; a queue of crawls.
- The utility modes `--serve-markdown`, `--serve-offline`, `--html-to-markdown` as GUI features.
- Re-implementing the HTML report. The GUI shows scores, findings and tables natively and opens
  the generated HTML report in the default browser.
- Installer, auto-update, code signing, an embedded exe icon.
- Changes to the crawler's behaviour, its CI workflows or its release process.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Toolkit | **egui / eframe** (wgpu renderer), `egui_extras` tables | Pure Rust, one self-contained exe, no WebView/Node runtime, fast virtualized tables, headless UI tests with `egui_kittest`. Considered: iced (weaker tables), Slint (DSL + licence terms), Tauri (frontend not Rust). |
| Execution model | The GUI **spawns `siteone-crawler.exe` as a child process** | The CLI already ships the host protocol for this (`--events-file`, `--control-stdin`, `--ai-list-models`, `--ai-check`, see `docs/EVENTS.md`). Crash isolation, clean stop semantics, and the crawler's process-global state stays out of the GUI. |
| Option metadata | The GUI **links the `siteone_crawler` library** and reads `options::core_options::get_options()` | Forms, defaults, help texts and validation come from the same code the CLI uses. No hand-maintained option list. |
| Validation | In-process `core_options::parse_argv()` before every start | The exact argv is validated by the CLI's own parser; the error is shown inline, before a process is spawned. |
| Layout | Cargo **workspace**, new member crate `gui/` (`siteone-crawler-gui`), `default-members = ["."]` | One lock file and one target dir; plain `cargo build/test/clippy/fmt` at the root keep targeting the crawler only, so CI and the pre-commit hook behave as before. |
| Async | No tokio in the GUI. `std::thread` + `std::sync::mpsc`; workers call `egui::Context::request_repaint` | Simple, deterministic, easy to test. |
| Secrets | OS credential store (`keyring`, Windows Credential Manager) | Passwords and API keys are never written to profiles, history or logs. |

Constraints that follow from these decisions:

- **Feature unification.** The GUI crate must not enable a feature on a shared dependency that
  changes the crawler when both are built together — in particular **never
  `serde_json/preserve_order`**. Where key order matters (table columns in the result JSON),
  deserialize with a map visitor into a `Vec<(String, T)>`.
- **`get_options()` has a side effect**: it creates `./tmp` in the current directory. The GUI sets
  its working directory to its data directory at startup, before the first call. `gui/tmp/` is
  git-ignored for test runs.
- **Never commit.** Implementation leaves all changes uncommitted (repository policy).

## 4. Process contract

### 4.1 Locating the crawler

Order: the path in Settings → `siteone-crawler(.exe)` next to the GUI executable → `PATH`.
The GUI runs `<bin> --version` (exit code 2 is the CLI's normal code for it) and shows the
version. If it differs from the linked library's `version::CODE`, Settings shows a warning
("option list may differ"); starting is still allowed. No binary → Start is disabled and a banner
on the Setup page offers **Locate…**.

### 4.2 Starting a run

Each run gets a directory `<runs>/<run-id>/` with `run-id = YYYYMMDD-HHMMSS-<host>` (sanitized,
numeric suffix on collision). The child's **working directory is the run directory**, so every
relative output path (and the CLI's `tmp/…` defaults) lands inside it. A relative **input** path is
made absolute before validation (§5.2), so the child reads the file the app checked.

The child's argv = the configuration's options (§5.2) + the **managed options**:

| Option | Value |
|---|---|
| `--events-file` | `<run>/events.ndjson` |
| `--control-stdin` | set |
| `--output` | `text` |
| `--force-color`, `--console-width=160`, `--hide-progress-bar` | set |
| `--output-json-file` | `<run>/result.json` |
| `--output-html-report`, `--output-text-file` | `<run>/report.html`, `<run>/output.txt` — only if the user did not set them |
| `--http-cache-dir`, `--ai-cache-dir` | shared `<data>/cache/http`, `<data>/cache/ai` — only if the user did not set them (and no `--no-cache`) |
| `--ai-api-key-env` | `SITEONE_GUI_AI_API_KEY`, with the key placed in the child's environment — only when AI is on, a key is stored, and the user set neither `--ai-api-key-env` nor `--ai-api-key-file` |
| `--config-file` | `<data>/empty-config.conf`, an empty file (rewritten empty when missing or not empty) |

**No ambient CLI config.** Without `--config-file` the CLI merges `~/.siteone-crawler.conf` (else
`/etc/siteone-crawler.conf`) under its argv; an explicit `--config-file` replaces that lookup (the
first one counts, `merge_config_file_args`). The app names its empty file for the validation (§5.2),
every run, every retry child (§4.9) and both AI tools (§4.6), so Setup's defaults are the effective
ones: a home config file applies to the CLI, not to the app. To use one, import it (§5.2). Like the
other managed options, `--config-file` is not in the command preview or its copies (they are for use
outside the app); `run.json`'s argv has it.

Spawn details: arguments are passed as a vector (no shell, no quoting); `stdin`, `stdout`,
`stderr` are pipes; on Windows the child is created with `CREATE_NO_WINDOW`. The GUI **never
assumes an output file name**: it learns every output from `artifact` events (the name can carry
a host or timestamp suffix).

### 4.3 While it runs

Three worker threads feed one `mpsc` channel of `RunMsg`:

- **events tail** — follows `events.ndjson` from offset 0 (poll ≤ 100 ms), splits on `\n`, keeps a
  partial last line for the next read, deserializes each line. Unknown `type` values and unknown
  fields are ignored; a malformed line is counted and skipped. After the process exits the tail
  reads to end of file once more, then stops.
- **stdout reader**, **stderr reader** — raw bytes → `ansi.rs` → styled lines. `\r` rewrites the
  current line. Sequences split across reads are handled. The raw text is also appended to
  `<run>/console.log`.
- **waiter** — reports the exit code.

The UI thread drains the channel every frame (bounded per frame) into `RunState`. This happens in
`App::logic`, which eframe also calls while the window is minimized or covered (when it does not
call `ui`), so a run is pumped, finalized and recorded, and a close request answered, then too.

### 4.4 Stopping

- **Stop** writes `stop\n` to the child's stdin. State becomes *Stopping…*; the crawler still
  analyses and reports what it has (`runFinished.outcome = "cancelled"`).
- While stopping, the button becomes **Force quit** (confirmation) → kills the process.
- Closing the window during a run asks: *Stop the crawl and close* / *Cancel* (a window closed
  from the taskbar while minimized is restored to ask). On confirm the child is killed and the
  run is recorded as aborted. When the app exits any other way, what the crawler already reported
  is applied first: a run that has ended is recorded with its own outcome, an active one is
  killed and recorded as aborted.
- On Windows the child is put into a **Job Object with kill-on-close**: the crawler and everything
  it starts (Chromium in `--browser` mode) end with Force quit, with the drop of the run handle and
  with the GUI process itself, even when it crashes. (Independently, the closed stdin pipe makes
  the crawler stop by itself — protocol guarantee.) A run cut short by a crash of the GUI keeps its
  initial `run.json` and is listed in History as not finished.

### 4.5 Outcomes

| Observation | Run outcome shown | Stored in history |
|---|---|---|
| `runFinished` `success` | Finished | yes |
| `runFinished` `cancelled` | Stopped | yes |
| `runFinished` `qualityGate` | Quality gate failed | yes |
| `runFinished` `failed` | Failed — with `error` | yes |
| exit code 3 | No pages crawled — with hint (DNS, timeout, URL); when the first request ended with status -4 (the server closed the connection without an answer), the hint suggests setting a User-Agent | yes |
| exit code 101, no events | Configuration error — the CLI's `ERROR:` text in a dialog, back to Setup | no (run dir removed) |
| exit without `runFinished` | Crashed (exit N) / Aborted (killed by the user) — last console lines shown | yes |
| spawn error | Dialog with the OS error | no |

### 4.6 One-shot tools

`tools.rs` runs the binary with a timeout, without a console window, on a worker thread:
`--version`; `--ai-list-models` and `--ai-check` with the connection options of the current
configuration (input paths absolute, key via environment and the empty `--config-file` as in §4.2).
Both AI modes print exactly one JSON object on
stdout, also on failure (`{"ok":false,"error":…}`); the GUI shows `error` verbatim.

### 4.7 External link check

The crawler never requests anything on another host. The **app** checks a run's external links
after the crawl (`backend/link_check.rs`, no egui; workers + `mpsc` + waker like the runner).

- **Which links, with link data** (`--link-details`, the app's default): the result JSON's `links`
  table — every URL on another host that a page links to with `<a href>` (the others are external
  files, counted), with every kept referring page (up to 50) and `inLinks` as the count, most
  referring pages first, at most 2,000 links.
- **Which links, without** (`model/link_check.rs::link_list`): the result JSON's `skipped` table (rows with
  reason `Not allowed host`; `sourceAttr` tells a link, `<a href>`, from a file; `sourceUqId` is the
  page without the start URL's scheme and host) joined by URL with `external-urls` (`count`;
  `foundOn` = full URLs joined by `", "`, ` (+N)` for more). A URL only one table has is used too
  (without a `skipped` row, its extension decides). `http`/`https` only, fragments dropped,
  de-duplicated, at most 20 source pages per link, at most 2,000 links (the rest is reported).
  External files (images, scripts, styles, fonts, …) are counted, not requested. The crawler keeps
  one entry per URL — the first page and the first attribute it was found with — so a URL first met
  as `<link href>` counts as a file.
- **One check per link**: one `GET` following at most 10 redirects (the chain is that one check).
  Headers: a User-Agent — the run's `--user-agent` with its trailing-`!` rule, else a current desktop
  Chrome string plus `SiteOne-Crawler/<version>` — and `Accept: text/html,*/*`. Never the site's
  `--http-auth`, `--header` values or cookies. The run's `--proxy`; its `--timeout`, at least 10 s,
  for the whole request. Certificates are always verified (an invalid one is a TLS error).
- **Reading the answer**: the final status and URL; only for an OK HTML answer at most 256 KB of the
  body (less once `</title` has arrived), from which the `<title>` is taken (UTF-8, else Latin-1;
  common entities decoded, whitespace collapsed, at most 200 characters). Nothing else is parsed or
  requested.
- **Outcome**: *OK* (below 400 after the redirects), *Refused* (401, 403, 429: an automated request
  was turned away — flagged, not called dead), *Broken* (other 4xx/5xx, or no answer: DNS,
  connection, TLS, timeout, too many redirects, other). Kept per link: status, failure, final URL,
  title, time, the pages it was found on.
- **Politeness**: 4 workers; one request at a time per host and at least 500 ms between two
  requests to one host.
- **A server that does not answer** is asked twice, not once per link (`HostHealth`, kept per
  scheme, host and port for the length of one check): when a server has never sent an HTTP answer
  and two requests to it failed with a connection error, a TLS error or a timeout — or one DNS
  lookup failed — its remaining links are not requested and get the same failure, with "Not
  requested: <host> did not answer the earlier requests" as the error text. A server that has
  answered once is never given up (a later timeout is a slow page). A retry pass (§4.9) follows
  the same rule for crawled URLs and external links; a URL it does not request stays queued with
  that reason.
- **Lifecycle** (`app/links.rs`): with *Check external links* on, the check starts by itself once the
  crawl has ended and its result JSON is loaded; *Check external links now* runs it for any finished
  run. One check at a time. The crawl's outcome and History record do not wait for it. *Stop check*
  keeps what was checked (marked stopped); closing the app stops it and writes what it has without
  waiting for requests in flight; deleting the run drops it. A panic in a check is caught (an
  internal-error result).

### 4.8 Link texts

**From the crawler** (`model/link_data.rs`): every `url` event names the page that queued the URL
(`source`, `sourceAttr`; with `--link-details` also `linkText`, `sourceLine`, `sourceColumn`), so
*Found on* is known as each URL arrives, for every status. With `--link-details` the result JSON's
`links` table lists every referring page of every URL (up to 50, the queueing page first, with the
total `inLinks`) with its link text and position. The link text is the crawler's; a reference
without one is named by its attribute (`<script src>`, `redirect`), one in a stylesheet "in a
stylesheet". The position is the crawler's line and column in the page as it received it; the
crawler does not report the length of the line, so a column beyond 500 (a minified file) is shown
too (`style.min.css:1:20345`), any other reference by its line. Pages the crawler reported a
position for are **not fetched again**.

**The app's own reading** is the fallback (`backend/link_text.rs`): the app fetches a page a broken
or external link was found on and reads the text of the link that points to it and where in the
file it is — only for a reference the crawler gave no position for that the reading can locate (an
HTML attribute or a stylesheet's `url()`: a run without `--link-details`, a page rendered with
`--browser`), and for a run of a crawler without link data (its `404` table, as before). References
found in scripts, sitemaps or redirects are never fetched for. A run with complete crawler data
makes no request.

- **Which pages**: after a crawl, the pages above of the broken crawled URLs (the `404` table's
  `sourceUqId` for runs of an older crawler); once the run's external links are checked, also the
  pages of the external links without a crawler position. Each page is
  fetched once per run; what it says about every target the run knows is kept. At most 200 pages
  per run (the rest is reported). A *found on* that is a stylesheet (a missing font or background
  image referenced by `url()`) is fetched like a page and counts within the same 200.
- **Only the crawled site**: a page whose host is not the start host (`www.` aside) is never
  requested; redirects (at most 10, followed by the app) only within the site. Like the crawler:
  the User-Agent rule of §4.7, `--proxy`, `--timeout` (≥ 10 s), `--accept-invalid-certs`. One page
  at a time, 500 ms apart; HTML and CSS only (by `Content-Type`, else a `.css` path); at most 2 MB of
  a page and 8 MB of a stylesheet read (an unminified framework bundle can outgrow a page; a
  reference beyond the cap is not found).
- **Credentials**: `--http-auth` and the `--header` values go with a request — the first and each
  redirect, judged on its own URL — only where the crawler sends them
  (`ParsedUrl::may_send_credentials`: not from https to http; for an IP address or a single-label
  host such as `localhost` only to the start port). A page of the site outside that boundary is
  fetched without them. They are the run's own: the current run keeps a copy in memory (never
  written), so a later change in Setup or another profile does not reach its requests. A run from
  History keeps neither (§5.6): when it used them, its source pages are not fetched, and the
  reason names what is missing — no value of the session takes their place.
- **The text**: the elements that reference the target (`a`/`area[href]`, `img[src|srcset]`,
  `source[src|srcset]`, `script[src]`, `link[href]`, `iframe[src]`, `video[src|poster]`,
  `audio[src]`), URLs resolved against the page and `<base href>` and compared normalized (scheme
  and host case, default port, fragment, trailing slash, percent-encoding). `<a>`: its text,
  whitespace collapsed (around an image without text: `[image: alt]` / `[image]`); `<area>`/`<img>`:
  `alt`; otherwise the tag (`<script src>`). Up to three different texts joined by ` | `, at most 200
  characters. A page that does not reference the target: *not found on the page*. A reference
  the elements above do not cover (an inline `style`, a `<style>` block, `<object data>`, …) is
  named by what it is (`<div style> url()`). A stylesheet has no link text: *in a stylesheet*
  (*not found in the stylesheet* when it no longer references the target).
- **The position** of the reference in the file as fetched, kept next to the text: the first
  reference's line and column (1-based, in characters, where the URL text starts) and how many
  references the page has. Found by a tolerant scan of the raw text (the HTML parser gives no
  positions): in HTML, the attribute values that hold URLs (`href`, `src`, `srcset` items,
  `poster`, `<object data>`, `action`, `<meta content>`, …), entities decoded before the value is
  resolved, and the `url()` of inline `style` attributes and `<style>` blocks; in a stylesheet,
  `url()` (quoted or not) and `@import "…"`, resolved against the stylesheet's own URL. Comments
  and the text of `<script>` are skipped. URLs are resolved (`<base href>` honoured) and compared
  as for the text. Shown as `…/page-styles.css:1929`; a reference on a line longer than 500
  characters (a minified file) as line and column, `style.min.css:1:20345`. Honest limits: the
  position is in the file as fetched after the crawl; a page that changed since, or a link that a
  script builds, has none (the cell is as without it).
- **External links**: their *found on* pages (from `external-urls`, any number) are fetched under
  the same rules — once the run's external links are checked, pages of the crawled site only,
  within the same 200 — and get positions there; no request is added for positions.
- Without `--link-details` the app knows only the first page that referenced a URL (the event's),
  and for runs of an older crawler only for 404s.

### 4.9 Retry queue

After a run has finished, single URLs can be requested again without crawling the site again
(`model/retry.rs`, `backend/retry.rs`, `app/retry.rs`). A URL is *retryable* when the Link checker
tab lists it: a crawled URL that failed (4xx/5xx or no answer), or an external link of the check.
The app does not keep track of what was retried: a retry's answer replaces the URL's answer, and the
views show what is still broken.

- **Queue**: an ordered set of URLs per run. Adding a URL twice keeps one entry. The queue and
  every retry result are kept in `retries.json` in the run folder, written after each change and
  each URL, so they survive a restart and belong to a run opened from History as well.
- **A pass** takes a list of URLs — the whole queue (*Retry queue*) or the chosen rows (*Retry
  now*) — and requests them one after another: one request at a time, at least 500 ms between the
  end of one request to a host and the start of the next (more when the run's `--max-reqs-per-sec`
  asks for it: 1 / rate). A URL leaves the queue when it has an answer. URLs added during a pass
  wait for the next one. **Stop** ends the pass after killing the request in flight; that URL and
  the rest of the pass stay (or become) queued. Leaving a run from History while its pass runs
  stops the pass the same way.
- **A crawled URL** is requested by the crawler itself, so that the answer is what a crawl would
  get: one child process per URL (started like a run, §4.2–4.4: no shell, no console window, Job
  Object), working directory the run folder, its events and result JSON in `<run>/.retry/`, which
  is removed afterwards. Its argv is the URL, the run's request options and the options that
  limit the child to that one request:

  ```
  --url=<URL>  <request options of the run>
  --http-cache-ttl=0s                      (only when the run's cache is on)
  --max-visited-urls=1 --disable-all-assets=true --ignore-robots-txt=true
  --analyzer-filter-regex=/^SeoAndOpenGraphAnalyzer$/  --config-file=<data>/empty-config.conf
  --events-file=<run>/.retry/events.ndjson --output=text --hide-progress-bar=true
  --output-json-file=<run>/.retry/result.json --output-html-report= --output-text-file=
  ```

  Checked against a local server that logs every request (crawler 2.7): a page with images,
  scripts, a stylesheet and links is requested alone; a redirect is reported as the answer (301)
  and its target is not requested; no robots.txt is requested. `--analyzer-filter-regex` keeps
  only the analyzer whose `seo` table gives the title of an OK HTML answer; the DNS and SSL/TLS
  analyzers, which open connections of their own, do not run. One process per pass with
  `--url-list` was tested and is not used (`core_retry.rs` pins why): it sends one request per URL,
  but spaces only the starts of requests (no 500 ms after a slow answer) and requests every URL of
  a host that does not answer. The request options are taken from
  the run's argv and pinned by a unit test that fails when the CLI gains an option the list has not
  classified: `--device`, `--user-agent`, `--timeout`, `--proxy`, `--http-auth`, `--header`,
  `--accept-invalid-certs`, `--accept-encoding`, `--resolve`, `--transform-url`,
  `--add-random-query-params`, `--max-url-length`, `--http-cache-dir`, `--http-cache-compression`,
  `--no-cache`. `--http-auth` and `--header` go only to a URL the crawl sent them to (the crawler's
  own rule, `ParsedUrl::may_send_credentials`: the start host, `www.` aside; not from https to
  http). They are the values the run was started with (the current run's argv, in memory), never
  Setup's. None of the run's exports, AI steps, browser rendering or outputs are passed.
- **The answer** is the child's `url` event: status, content type, time, size; the title of an OK
  HTML answer from the `seo` table of its result JSON. The exit code does not matter: a 404 ends
  with exit code 0, a URL without an answer (a refused connection, status -1) with exit code 3 and a
  `runFinished` of outcome `failed` — both are answers.
- **The HTTP cache**: the child uses the run's cache directory with `--http-cache-ttl=0s`, so it
  reuses no stored answer that is a second old or older and stores its own (every real request
  overwrites the stored entry). An answer the child reports as `cached` (an entry written less than a
  second before) is not a retry: the URL is requested once more with the cache off. A later crawl
  with the same settings gets the retried answer from the cache only where its request has the same
  cache key as the child's. The child's request has no `Origin` header (a start URL never has one),
  and `Origin` is part of the key. An **image** never gets the header, so a later crawl always sees a
  retried image (and the start page). A **page or other file found as a link** gets the header only
  when the page it was found on is already recorded at that moment (`src/engine/crawler.rs`,
  `get_origin_header_value_by_source_uq_id`), which depends on timing: the later crawl may get the
  retried answer, request the URL again, or reuse its own stored answer of the earlier crawl — a
  stored 404 or 403 for the cache's lifetime (`--http-cache-ttl`, 24 h by default); stored 429, 5xx
  and failed requests are never reused. (The reused 404 and the repeated request were both
  observed with one local server; a test pins the image and allows the three for the page.)
- **An external link** is checked again exactly as in §4.7 (one `GET`, no site credentials); the
  new answer replaces the link's entry in `external-links.json`.
- **A run whose configuration is incomplete** — opened from History after using `--http-auth` or
  `--header`, which History does not keep (§5.6) — retries external links only; a crawled URL is
  not requested, it stays queued with the reason, which names what is missing. A password in Setup
  never takes the place of the run's: it may belong to another site.
- **Results**: per URL the newest answer, and the first one (the crawl's or the check's, never
  overwritten), which tells whether a retry changed what the crawler's outputs show. A URL that
  answers OK now simply leaves the broken views. A URL that could not be retried (no crawler binary,
  the child ended without a `url` event, a watchdog of the run's timeout plus 30 s, an incomplete
  configuration) keeps its old answer, stays queued and shows the reason.
- **What a retry changes**: the URL's row on the URLs and Link checker tabs (the run's URL row and
  its counters take the newest answer), the counts of the tabs, views, tiles and status breakdown,
  the History record's numbers (errors, bytes), and the link report (§4.10). **What it cannot
  change**: the crawler's own outputs — the HTML report, the result JSON, the text output, the
  scores, findings and analysis tables. They describe the crawl as it ran, and a page that answers
  now was not analysed and its links were not followed. The app says so wherever those outputs are
  shown once a retry has given a crawled URL another status, and offers **Run again**.
- **Not while**: a crawl is running, or the run's external links are being checked, or another pass
  runs (the buttons are disabled with the reason). Starting a crawl stops a pass; what was not
  retried stays queued. Closing the app ends the pass (the child dies with the Job Object) and
  writes the queue. Deleting the run drops the pass. A panic in a pass is caught (an error on the
  URL).

### 4.10 Link report

The crawler's reports contain neither the app's external link check nor link texts nor the answers
of retries.
The app writes its own report of a run's links, `link-report.html` in the run folder
(`model/link_report.rs`, gathered in `app/report.rs`): one self-contained HTML file (no script, no
external resource, light and dark by `prefers-color-scheme`, printable).

- **Content**: what is broken now — retries included: a URL that answers OK after a retry is not
  in it. The site, when it was crawled, when the report was written; the counts (broken internal
  pages, broken internal assets, broken external links, refused external links, external links
  checked); **What was checked**; then one table per group that has rows — broken internal pages,
  broken internal assets, broken external links (an older run's crawled external URLs included),
  refused external links — and, folded (`<details>`), the working external links. Columns: status,
  URL, title or kind, link text, found on — each page with where it references the link
  (`…/page-styles.css:1929`, "(and 2 more)" for further references on that page; the link opens
  the page without it), then "and N more pages" beyond the 50 the crawler lists. Last, **Broken
  links by page**.
- **What was checked** (`model/coverage.rs`): *Scope* — the start host, with or without `www.`, and
  the `--allowed-domain-for-crawling` and `--include-regex` values of the result JSON's `options`;
  *Crawled URLs* — the number and the newest answers by class ("268 OK (2xx), 1 redirect (3xx),
  6 client errors (4xx), 1 without an answer (connection failed, timeout)", zero counts left out);
  *External links* (when checked) — OK (how many after a redirect), refused (401, 403, 429), broken
  (4xx, 5xx), without an answer; *Not checked* — one sentence each, a count only where the data has
  one, else "Nothing that the crawl's data names":

  | Gap | Source | Count |
  |---|---|---|
  | the crawl did not finish (Stopped, Aborted, Crashed, Failed, No pages crawled) | outcome | — |
  | the crawl reached `--max-visited-urls` (URLs crawled ≥ the limit) | `options` | — |
  | only the start page (`--single-page`); pages deeper than `--max-depth` | `options` | — |
  | cart and action links (the app's patterns, §5.2) | `options.ignoreRegex` | — |
  | URLs matching the user's own `--ignore-regex` patterns (named) | `options.ignoreRegex` | — |
  | disallowed by robots.txt; any other reason of the crawler's skip list, verbatim | `skipped-summary` (or `skipped` rows) | yes |
  | content types not downloaded (`--disable-images`, …) | `options` | — |
  | external links found but not checked; over the app's cap | link list, check | yes |
  | files on other websites (the app checks links only) | link list | yes |

  The crawler drops URLs that match `--ignore-regex`, lie beyond `--max-depth` or come after
  `--max-visited-urls` without listing them, so those gaps never carry a number.
- **Broken links by page**: the rows of the groups above that are broken or refused, grouped by
  the page they were found on, as *By page* in the Link checker tab: a heading per page (a link,
  the number of links), its links (status, URL, title or kind, line on that page, link text); a link found on several
  pages under each; pages with more links first, then by URL; the links of no known page last
  under "Page not reported by the crawler" with the reason. Left out when it would only repeat the
  groups — a single group (all on one page, or no page known) or no page known — and when nothing is
  broken.
- **Written** when the crawl's result is loaded, when a link check ends, when link texts arrive,
  after every retry pass, and when it is opened — always from the current state, atomically, only
  into an existing run folder.
- **Safety**: every value from the web is HTML-escaped (text and attributes); only `http`/`https`
  URLs become links.
- It is a file of the run: on the Files tab (*Written by the app*: Open, Show in folder), and
  **Link report** on the Link checker tab writes and opens it.

## 5. Data model

### 5.1 Option schema (`model/schema.rs`)

Built once from `get_options()`. For each option: name, short name, group, type, list-ness,
default, description, nullable, numeric range (`extras`) — plus GUI annotations kept in small
tables in this module:

- **visibility**: `Editable` (default) · `Managed` (set by the GUI, §4.2: `--events-file`,
  `--control-stdin`, `--output`, `--force-color`, `--no-color`, `--console-width`,
  `--hide-progress-bar`, `--output-json-file`) · `Hidden` (not a crawl setting: `--help`,
  `--version`, `--serve-markdown`, `--serve-offline`, `--serve-port`, `--serve-bind-address`,
  `--html-to-markdown`, `--html-to-markdown-output`, `--ai-list-models`, `--ai-check`;
  `--url` and `--ai-api-key` have dedicated fields).
- **choices**: fixed value sets for string options, shown as a dropdown or as check chips for
  lists (`--device`, `--ai-provider`, `--ai-actions`, `--ai-report`, `--ai-schema-enforce`,
  `--ai-elaborate-template`, `--ai-profile-template`, `--result-storage`, `--browser-wait`,
  `--screenshot-mode`, `--screenshot-format`, `--screenshots-animation`, …). Values are taken
  from the option descriptions / the crawler's validation code.
- **secret**: `--http-auth`, `--mail-smtp-pass`, `--upload-password`, `--ai-api-key`.
- **path role**: `Dir` · `OutputFile` (save dialog) · `InputFile` (open dialog: `--url-list`,
  `--ai-prompt-file`, `--ai-api-key-file`, `--ai-schema-file`, `--ci-baseline`, `--browser-path`,
  `--ffmpeg-path`).

A unit test fails when an annotation names an option that does not exist, so a renamed CLI
option is noticed at once.

Widget per type: `Bool` → toggle · `Int`/`Float` → numeric field (range-checked) · `String` →
text or dropdown · `SizeMG`, `Email`, `Url`, `Regex`, `HostAndPort`, `ReplaceContent`, `Resolve`,
`HttpHeader` → text with a format hint · `File`/`Dir` → text + **Browse…** · list options → a
row editor (add, remove, reorder not needed) · secrets → password field with reveal.

### 5.2 Configuration (`model/config.rs`)

```
CrawlConfig { url: String, ai_enabled: bool, check_external_links: bool, skip_action_links: bool,
              values: BTreeMap<OptionName, Value> }
Value = Bool(bool) | Text(String) | List(Vec<String>)
```

`check_external_links` is a setting of the app (§4.7) with no CLI equivalent: `to_argv`, the
preview and the run plan emit nothing for it. It is stored with the configuration (session,
profiles, run snapshots, *Run again*) and only when on.

`skip_action_links` (*Skip cart and action links*, default **on**) maps to the CLI: while on, the
argv's `--ignore-regex` gets `config::ACTION_LINK_PATTERNS` after the user's own values (a pattern
the user has already is not repeated), so the command preview, the exports and `run.json`'s argv
carry them. The crawler matches `--ignore-regex` against the full URL of every found link (entities
decoded; `/…/` delimiters, `fancy_regex`) and neither requests nor lists a match — checked with the
real crawler and a logging server: none of the links below is requested, the `skipped` table stays
empty.

| Pattern | Software | What the GET does |
|---|---|---|
| `/[?&]add-to-cart=/` | WooCommerce | adds a product to the cart (seen: 154 of 172 crawled HTML URLs of a shop, ~4 s each) |
| `/[?&]remove_item=/` | WooCommerce | removes an item from the cart |
| `/[?&]undo_item=/` | WooCommerce | puts a removed item back |
| `/wp-login\.php\?(.*&)?action=logout/` | WordPress | logs out (ends a session a crawl with a login cookie uses) |

`?replytocom=` (WordPress comment replies) is not in the list: a crawler trap that duplicates a
page, but it changes nothing; it stays the user's own `--ignore-regex` choice. Stored like the other
switch, only when off; a configuration stored before it existed gets the default (on). Import: a
command that contains every pattern gets the switch (on) instead of them, so a run never passes them
twice; a command without them gets the default (on), like a missing `--timeout`; a command with only
some keeps those as the user's own. The switch counts in Scope's "n changed" and in the profile's
modified state when off, not in the command's count of changed options. *Reset all* keeps it (as
it keeps the other app settings).

`values` holds **only what differs from the default** ("overrides"). Numbers are kept as
text and validated against the type.

The default of an option is the CLI's, with one exception (`schema::APP_DEFAULTS`): the app's
default **`--timeout` is 30** seconds (the CLI's is 5, too short for a slow site that has to build
a page its cache no longer holds). An option with an app default is passed on every run, also
with that default, so the command always says what the run does: a configuration without an
override emits `--timeout=30`, one set to 5 emits `--timeout=5`. A stored configuration or an
imported command without `--timeout` gets the app's default.

The same holds for **`--link-details`, on by default** (the CLI's default is off): the crawler then
reports every referring page of each URL with its link text and line (§4.8), which the Link checker,
the link report and the URLs tab use, and the app needs no second request of those pages. Every run
emits `--link-details=true` (or `=false` when turned off in Setup → Scope, *Record every referring
page*); a stored configuration or an imported command without it gets the default. The cost: a
larger result JSON on big sites (a generated 3,000-page site with about 60 links per page: 22 MB
instead of 0.9 MB, `docs/JSON-OUTPUT.md` §5.29). A retry child never gets it (§4.9).

- `to_argv(&schema, &secrets) -> Vec<String>`: `--url`, then overrides in schema order, one
  `--name=value` element per value; list options use the form that round-trips every item
  exactly (see `options/option.rs`: repeated options and the literal-array `--name:=value` form);
  booleans use the syntax the parser accepts for both `true` and `false`. With `ai_enabled =
  false` no option of the AI group is emitted.
- **Round-trip requirement:** for every option and for adversarial values (spaces, commas,
  quotes, `=`, `:=`, non-ASCII), `parse_argv(to_argv(config))` yields exactly the configured
  values. This is a unit test against the linked crawler library.
- `validate()` = URL shape check (`http://` or `https://`; a missing scheme is completed with
  `https://` on blur) + `parse_argv` on the full argv including managed options and the empty
  `--config-file` (§4.2).
- **Input paths.** The value of an option with the `InputFile` role (§5.1: `--url-list`,
  `--ai-prompt-file`, `--ai-api-key-file`, `--ai-schema-file`, `--ci-baseline`, `--browser-path`,
  `--ffmpeg-path`) that is a relative path names a file in **`<data>`**, the app's working directory
  (where an in-process check of it looks too). `with_absolute_inputs(&schema, base)` makes it
  absolute; Setup keeps what was typed, and everything a crawler gets uses the result
  (`App::run_config`): the validation, the run plan and the run's configuration snapshot (*Run
  again*), the AI tools, the command preview and its copies, the exported config file. A bare
  program name in `--ffmpeg-path` (no `/` or `\`) is looked up on `PATH` and stays. Output paths and
  directories stay relative (they land in the run folder, §4.2). An imported config file's relative
  input paths name files next to it: made absolute against its folder on import.
- Import: a CLI config file (one argument per line, `#` comments) or a pasted command line →
  `CrawlConfig`; unknown options are listed to the user, not dropped silently. A pasted command is
  split with the quoting rules of PowerShell and of Bash (`split_command_line`) — the shells the app
  exports for — and `read_command_line` decides which reading applies (`CommandLineReading`):
  **same** argv from both → imported, no shell named; **only one** shell reads it → that one,
  named ("Read as PowerShell", with the other shell's reason); both read it **differently** → the
  signs in the text decide (`shell_hints`), and the dialog names the reading, the sign and the
  first argument the other shell would read differently, with *Import as Bash instead* (or
  PowerShell) one click away. PowerShell signs: a backslash before a letter, digit, `.`, `_` or `-`
  outside quotes (a path, which Bash would take as an escape), a doubled single quote inside single
  quotes, a backtick before a line break or inside double quotes, the call operator `&` before the
  program. Bash signs: a backslash before a line break, `'\''`, `\"` `\$` `\\` inside double quotes,
  `$'…'`, an argument that goes on after the quoted string it starts with (PowerShell makes two of
  it). No sign, or signs of both → **no guess**: the dialog shows how each shell reads the first
  differing argument and offers *Import as PowerShell* and *Import as Bash*, neither preselected.
  **Neither** reads it → Import is off and both errors are shown, the more plausible shell's first
  (by the signs; PowerShell without one). The app never imports a value that differs from what the
  shell would pass without saying so. What the app copied for either shell is read back as that
  shell, or as both alike, with its argv (unit test: Windows paths, apostrophes incl. typographic
  ones, spaces, quotes, backticks, `$`, line breaks, continuation lines, a configuration as
  exported). PowerShell, read as PowerShell 7.3+ passes it to a program
  (checked against the real shells, §8): `'…'` literal with `''` for `'`; `"…"` with backtick
  escapes and `""`; outside quotes a backtick escapes the next character the same way, between
  arguments before a line break it continues the line; an argument that starts with a quoted
  string ends with it (`'a'b` is two); `#` or `<#…#>` at an argument's start is a comment; Unicode
  whitespace separates. Refused with the reason, never guessed: a variable or expression (`$name`,
  `$(…)`, `@…`), an unquoted `;` `|` `&` `(` `)` `{` `}`, a redirection, a comma next to a space,
  quote or comma (a list, passed differently by 5.1 and 7), an argument starting with a single dash
  that PowerShell splits at `.`, `[` or a backtick (`-t=5.5`), `--%`, a line break without a
  continuation followed by more, `` `0 ``, and `` `e `` / `` `u{…} `` (5.1 and 7 differ). Bash, as
  Bash reads a command's arguments (`split_bash`): blanks separate, adjacent parts form one; `'…'`
  literal; `"…"` takes `\` only before `$` `` ` `` `"` `\` and a line break; `$'…'` with the C
  escapes (`\n`, `\t`, `\'`, `\xHH`, `\u…`, …); outside quotes `\` escapes the next character and
  before a line break continues the line; `#` at an argument's start is a comment. Refused with the
  reason: a variable, expansion or command substitution (`$name`, `${…}`, `$(…)`, `` `…` ``,
  `$"…"`), an unquoted `;` `|` `&` `<` `>` `(` `)` `{` `}`, `~` at an argument's start, a `!` that a
  terminal's Bash reads as a history reference, a line break without a continuation followed by
  more, a `$'…'` that decodes to a NUL or to bytes that are not UTF-8. Glob characters (`*` `?`
  `[`) are taken as written (a pattern that matches no file is passed so; an option argument
  `--name=…` names none). Nothing is run in a shell; cmd syntax is not read. It
  replaces the configuration with its passwords: `--http-auth`, `--mail-smtp-pass`,
  `--upload-password` the import does not contain are cleared, never carried to another site. The
  AI API key stays unless the import has one (it belongs to the provider, not to a site; as in
  *Reset all*). Saved profiles keep their passwords.
- Export: config-file text; command line quoted for PowerShell or for POSIX shells. Secrets are
  masked (`••••`) in previews and exports unless the user chooses *Include secrets*. The PowerShell
  command is for PowerShell 7.3 or later, where every value reaches the crawler exactly (an
  argument starting with a single `-` is quoted too: PowerShell would split `-t=5.5`). Windows
  PowerShell 5.1 passes a value with a `"`, an empty one, or one with whitespace ending in `\`
  differently, and no quoting is right for both: *Copy as PowerShell* says so in its tooltip and,
  when the command holds such a value, warns with the option names (`powershell_legacy_hazards`).

### 5.3 Presets (`model/presets.rs`)

The eleven presets of the CLI wizard (`PRESETS` of `src/wizard/presets.rs`, compiled into the GUI
by path, §3: Quick Audit, SEO Analysis, Performance Test, Security Check, Offline Clone, Markdown
Export, Stress Test, Single Page, Large Site Crawl, Sitemap Generator, Custom), converted to
override sets via the wizard's own `build_argv()`. Setup shows ten of them as cards; *Custom* (no
overrides) has no card. Applying a preset replaces the non-AI
overrides (after confirmation when the current configuration has unsaved changes) and keeps the
URL and the AI connection.

### 5.4 Live state (`model/events.rs`, `model/run_state.rs`)

`events.rs` mirrors `docs/EVENTS.md` (protocol 1) with `serde`: camelCase, optional fields
optional, an `Unknown` catch-all variant. `RunState::apply(event)` is a pure function of its
input and therefore also rebuilds a finished run from its `events.ndjson` (history).

`RunState` holds: run metadata; phase states (crawl / ai / analysis); `done`/`total`; URL rows
(compact struct per row, with the `url` event's depth and its referrer — page, attribute, link text,
line, column — whose strings are shared between rows; none from an older crawler); counters by status class and content type; total bytes; average and
maximum response time; URLs per second over the last 5 s; AI tasks (key → label, done, total,
state), AI request log, AI usage totals; artifacts; issues; console lines (ring buffer, 20 000
lines); final outcome.

### 5.5 Results (`model/results.rs`)

Typed view of the result JSON (`docs/JSON-OUTPUT.md`): `qualityScores` (overall + 5 categories
with deductions), `stats`, `summary.items`, `tables` (ordered columns, string rows), `options` (kept
as JSON: a value of an unexpected type never makes the file unreadable), and with
`--link-details` the `links` table and the link facts of the `results` rows (`depth`, `inLinks`,
`outLinks`), streamed row by row into a compact `LinkGraph` (target → kept referrers and total,
strings shared, looked up by hash) instead of a generic table — the `links` table is not in the
Tables tab. Loaded on a worker thread (a 3,000-page sample with 161,000 `links` rows, 54 MB:
0.2 s in a release build, 2 s in a debug build, 16 MB of heap at the peak, 15 MB kept); fields the GUI does not use are skipped; a missing or unreadable file yields an
explanatory state, not an error dialog. `docs/OUTPUT-crawler.siteone.io.json` is the test
fixture.

### 5.6 Persistence

| What | Where | Notes |
|---|---|---|
| Settings | `<config>/settings.json` | crawler path, runs folder, theme, UI scale, window size |
| Working configuration | `<config>/session.json` | autosaved (debounced) so a restart restores the form; its passwords in the credential store (session scope) |
| Profiles | `<config>/profiles/<slug>.json` | name + `CrawlConfig` |
| Runs | `<runs>/<run-id>/` | `run.json` (meta + configuration snapshot + summary numbers), `events.ndjson`, `console.log`, outputs |
| External link check | `<runs>/<run-id>/external-links.json` | per link: outcome, status, failure, final URL, title, time, pages found on; `complete: false` for a stopped check; loaded for past runs |
| Link texts | `<runs>/<run-id>/link-texts.json` | per source page: an HTML page read (target → text, target → position: line, column, count, long line), a stylesheet read (target → position), a stylesheet not fetched (files of earlier versions), or not fetched (why); the number of pages over the cap. Positions are optional: files of earlier versions load |
| Retries | `<runs>/<run-id>/retries.json` | the retry queue in order; per retried URL the first answer, the newest answer, the reason of a retry that could not be made (fields of older files, `retriedAt` and `retries`, are ignored) |
| Link report | `<runs>/<run-id>/link-report.html` | written by the app from the current state (§4.10) |
| Caches | `<data>/cache/http`, `<data>/cache/ai` | shared between runs |
| Secrets | Windows Credential Manager, service `siteone-crawler-gui`; with the `SITEONE_GUI_DATA_DIR` override `siteone-crawler-gui <hash of the folder>`, so two data folders never share secrets | account = `<profile-slug or "session">/<option>` |

`<config>` = `%APPDATA%\siteone-crawler-gui`, `<data>` = `%LOCALAPPDATA%\siteone-crawler-gui`,
`<runs>` = `<data>\runs` unless changed in Settings. `SITEONE_GUI_DATA_DIR` overrides both roots
(tests, portable use).

Rules: every JSON file carries `"schemaVersion"`; writes are atomic (temp file + rename); a file
that fails to parse is renamed to `*.corrupt-<timestamp>` and defaults are used, with a toast.
Secrets and environment values never appear in any file; the stored argv of a run is redacted.
The configuration snapshot in `run.json` also drops the userinfo of the URL and of `--proxy`,
`--upload-to`, `--ai-endpoint`, and leaves out the `--header` values (often cookies or tokens);
*Run again* replaces Setup's passwords with the run's: the current run's own (kept in memory with
the run, never written); none for a run from History, which names the passwords it used and its
headers as values to enter again — Setup's are cleared, not reused, since they may belong to another
site. The AI API key stays (named when the session has none). With unsaved changes in Setup,
passwords included, *Run again* asks first.
**Autosave** (`app/autosave.rs`) of the working configuration with its session passwords (one
value) and of the settings: a change is written after 800 ms without a further change, on a worker.
Writes are ordered — each has a generation; a write holds the order lock while it writes, and one
older than a write that has started is skipped — so an older value never replaces a newer one, in the
file or in the credential store. A value counts as saved only when its write succeeded. A failed
write (also a partial one: file written, password not — both are then written again) leaves the
value unsaved and shows an error toast on each failed attempt; it is written again after the next
change (800 ms), after a back-off (5 s, doubling to 60 s) and on exit. The exit flush takes part in
the order: it waits for a write that is running, a write that has not started is skipped, then it
writes the current value unless it is known to be stored.
Deleting a run removes only a directory that lies inside `<runs>` and contains `run.json`. Files of a
run are written only into a run folder that exists: a run deleted while its record, its check or its
link texts were being written is not created again.

## 7. Robustness requirements

1. No `unwrap`/`expect`/indexing on data that comes from files, the child process, the network or
   user input. A panic hook writes `<data>/crash.log` and shows a native message box — except for a
   panic the app catches and survives (a background task, a link check), which is only logged.
2. The UI thread never blocks: file loads, process calls and directory sizes run on workers.
3. Memory is bounded: console ring buffer; URL rows are compact; channel draining is bounded per
   frame; repaint requests are throttled.
4. All paths are handled as `PathBuf` (spaces, non-ASCII, long paths); nothing is passed through
   a shell.
5. Secrets never reach logs, previews (unless revealed), profiles, history or crash logs.
6. Every failure in §4.5 and every "unavailable" state in §6 has a visible, specific message
   that says what happened and what to do next.
7. The protocol rules of `docs/EVENTS.md` are honoured: unknown events and fields ignored,
   absent values tolerated.
8. Files of a run that background tasks write (`retries.json`, `external-links.json` after a retry,
   `run.json`, `link-report.html`) are written in the order the app asked for them: a write that
   comes late never replaces a newer one.

**UI tests** (`gui/tests/ui_*.rs`, `egui_kittest`): every page and tab renders at 1280×820 and
1000×640, light and dark, with empty, live and finished data, and writes a PNG snapshot to
`gui/tests/snapshots/`. Snapshots are **written and checked, not compared**: a test asserts that
the rendered image has the window's size and is not blank, then saves it for people to look at;
there are no reference images (they would differ per GPU and font set), so the folder is
git-ignored. Without a wgpu adapter the rendering is skipped with a message. Interactions —
typing a URL enables Start; a preset changes the form and the command preview; searching filters
the option list; resetting an option removes it from the preview; the URL table filters and
sorts; the Link checker tab filters and joins *Found on*; Stop → Force quit; closing during a run
asks first, also while the window is minimized; a finished run reopens from History after a
restart; every control on every page has an accessible name. The run-page tests drive a
scripted child through the `ChildControl` seam (and a scripted check through `CheckControl`);
`ui_start.rs`, `ui_run_e2e.rs`, `ui_link_check_e2e.rs`, `ui_link_data_e2e.rs` and `ui_retry_e2e.rs` use the real crawler binary when it is
built. `ui_link_check_e2e.rs` crawls a site on `127.0.0.1` that links to a second one on
`localhost`: the crawl makes no request to the second site; *Check external links now* and the
automatic check request each link once and nothing else; the dead link (with its link text) and the
working one (with its title) show in Link checker; the URLs tab shows page titles; the run reopens
from History after a restart. `ui_retry.rs` drives scripted passes (`App::retry_spawner`): selection
by checkbox, header checkbox and Shift range; Add to queue; Retry queue; the row leaves *All broken*
and the link report, and no view or link keeps track of it; the counts of the tab, the views, the
Overview and the History record; the notice and Run again; the queue and results of a run reopened from History after a
restart; the buttons disabled with their reasons while a check, a pass or a crawl runs, and a crawl
stopping a pass; an incomplete configuration retrying external links only; *By page* (a link of
two pages under both, the unknown page last, "on N pages", a link ticked under one page ticked
under the other, the header checkbox, the selection kept across the layouts, a filter naming a
page, Retry now from it, disabled in *All external*). `ui_setup.rs`: *Skip cart and action links*
on by default with its patterns in the command and nothing counted as changed; off removes them
and counts in Scope and the modified state; the user's pattern stays first; off survives a
restart. Snapshots `run-by-page*` show the layout (with a retry queue and a selection: the
fullest toolbar) and `setup-action-links` the switch. `ui_run.rs` (positions): a 404 found on a
page and one found on a stylesheet show `:212` and `:1929` after the page, the suffix whole in a
narrow window, "in a stylesheet" as the link text, the *Line* of each link by page, Copy list and
`link-report.html` with the positions; snapshots `run-broken-positions*` and
`run-by-page-positions*`. `ui_retry_e2e.rs` crawls
a site with a missing page, creates the page, retries the row from the Link checker tab with the real
crawler, finds the new answer in the row and the URL no longer in `link-report.html`. The UI tests turn link texts off (`App::fetch_link_texts`) where the
scripted runs name real sites, so no test makes a request outside the machine.

**Gates** — all must pass:

```
cargo fmt -p siteone-crawler-gui -- --check
cargo clippy -p siteone-crawler-gui --all-targets -- -D warnings
cargo test -p siteone-crawler-gui
cargo build --release                               # → target\release\siteone-crawler.exe
cargo build --release -p siteone-crawler-gui        # → target\release\siteone-crawler-gui.exe
cargo fmt -- --check && cargo clippy -- -D warnings && cargo test    # crawler unaffected
```

On Windows the crawler's own `cargo test` has failures that do not come from the GUI: its tests
pass `--config-file=/dev/null`, which does not exist on Windows (exit 101). CI runs them on
Linux (`ci.yml`, `ubuntu-latest`).

**Acceptance walk-through** on Windows 11: start the exe → enter a URL → *Quick Audit* → Start →
live progress → Finished → scores, findings, tables, URL filter → *Open HTML report* → restart
the app → the run is in History and opens with the same data → *Run again* → Stop mid-crawl →
*Stopped* with partial results.

Most steps are covered by the automated tests above (real crawler for start, stop, kill and
configuration errors; scripted child for the Run and History pages). They need a person at the
screen: the real window's close button and the taskbar close during a crawl, *Open HTML report* /
*Open folder* launching the browser and Explorer, the native file dialogs, the Windows Credential
Manager (tests use an in-memory store), and the look of the snapshots.

## 9. Implementation phases

| Phase | Scope | Leaves behind |
|---|---|---|
| 1 Core | Workspace, crate scaffold, `model/*`, stubs with final signatures for `backend/*`, minimal `app.rs`/`main.rs` that opens a window | compiles; unit tests green |
| 2 Backend | `backend/*`, integration tests against the real crawler | a run can be driven headlessly |
| 3 Setup UI | `app.rs`, `theme.rs`, `ui/nav.rs`, `ui/widgets/*`, `ui/setup/*`, `ui/settings.rs` | configure, validate, preview, profiles, settings |
| 4 Run UI | `ui/run/*`, `ui/history.rs`, wiring of the run lifecycle, UI tests + snapshots | the complete application |
| 5 Review | independent review against this spec, fixes, gates, release exe, `gui/README.md` | acceptance walk-through passes |
| 6 External links | the app's external link check (§4.7), link texts (§4.8), page titles on the URLs tab, the switch as an app setting | the crawler no longer crawls other sites for the check |
| 7 Retry queue | row selection, the retry queue and its passes (§4.9), the link report (§4.10) | failed URLs are retried one by one; the app's views and its report follow |
| 8 Coverage | *By page* in the tab and the report, *What was checked* / *Not checked* (§4.10, §6.3), *Skip cart and action links* (§5.2) | a report says what it did not look at; shops are crawled without their action links |

Phases 2 and 3 touch disjoint files and may run in parallel.
